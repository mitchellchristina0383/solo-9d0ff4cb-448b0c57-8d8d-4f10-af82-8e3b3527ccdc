# VPN 换线 · MTU 黑洞演练台（Flask + Docker Compose）

一个单页交互式演练工具，用来复现这个典型故障：

> VPN 换线后小包能通、大报表卡住。报文置 DF（禁止分片），一旦
> `载荷 + 封装开销 > 线路 MTU` 就在线路侧被丢弃；超长通知（ICMP too-big）
> 可能被过滤形成静默黑洞，只能等超时缩包。换线后载荷重新从起始值试发，
> 旧线在途报文的回执仍会到达，与新线回执乱序交错、区间重叠。

## 启动

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

镜像用 `python:3.12-slim`，入口为 `gunicorn -w 1 --threads 8`
（内存态演练，必须单 worker；多线程足够单人/小班使用）。
`compose.yaml` 带 `/healthz` 健康检查。

### 本地直接运行

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python app.py            # http://127.0.0.1:8000
```

跑测试：

```bash
pip install pytest
pytest                   # 20 个 API/引擎用例
```

## 页面能做什么

1. 填写 **报表字节数**、**起始载荷**、**超时缩包步长**；
2. 分别设置 **线路 A / B 的 MTU、封装开销、超长通知开关**，
   参数卡实时显示 `MTU - 封装开销` 的最大载荷以及起始包是否必超；
3. **发下一包** / 填数量 **连续发包** / **连续发完剩余新包**；
   连发提交后立即返回“已受理”，由后台**分批**发送，网页可设**批间隔**，
   每批最多 5 包；同一场演练同时只允许一次连发，可随时**停止连发**；
4. 连发进行中仍可 **单发**、给已发包 **投递回执**、**换线**；单发与连发都从
   `next_offset`（下一段未首发字节）取载荷，单发不占连发包数，到报表末尾
   按实发包数收尾；换线、有效缩包或重置生效后，旧连发剩余包立即停发；
5. 每个在途包可单独点 **回执 ACK** 或 **触发超时**；
   也可选择正序 / 逆序 / 随机乱序，**依次批量回执**，或只随机回一个；
6. 超长通知打开时，超大包被丢弃并产生“待投递通知”，由你手动点
   **投递超长通知**（可以先换线再投递，观察“过期轮次通知不缩包”）；
7. **换到线路 A/B 并立即重发**：载荷重置为起始载荷、轮次 +1，
   并按新载荷把所有未确认字节重新打包立即发出；
8. 表格显示每包的 **线路、轮次、类型、载荷长度、封装后长度、
   字节区间 `[起,止)`、协议状态与上帝视角的物理结果、操作按钮**；
9. 顶部实时显示 **累计确认字节数 / 总字节数 / 百分比**、合并后的确认区间、
   区间 chip 和覆盖图（绿色为确认区间，彩色描边为各包范围）；
   连发面板显示 **进行中连发的实发/请求包数** 和 **最近一次连发的实发包数与结束原因**；
10. `累计确认 == 报表字节数` 时显示“全部传完”横幅，并发新包/换线会被拒绝，
    重复/重叠回执保持幂等。

## 核心规则与实现对应

代码分两层：

- `drill_engine.py`：纯逻辑。`Drill`（演练状态）、`Packet`、
  `DrillConfig/LineConfig`、`AckedRanges`（合并区间并集与未确认打包）。
- `app.py`：Flask 路由 + 全局 `Drill` 单例 + `RLock`，所有响应回传完整 state。
- `templates/index.html`、`static/app.js`、`static/style.css`：原生 JS 单页，
  无外部 CDN/依赖，每 2.5s 轮询一次，所有写操作后立即用响应 state 重渲染。

关键语义：

- **字节编号**：从 0 开始，区间左闭右开，`[0,1400)` 即前 1400 字节。
- **DF 判定**：发包时计算 `wire = size + overhead`，`wire > mtu` 即物理丢弃：
  - 通知关 → `silent_drop`：发送端仍显示“在途”，且不允许 ACK（上帝视角标明
    实际已静默丢弃），只能由演练者点“触发超时”；
  - 通知开 → `notify_drop`：生成 pending 的超长通知，可手动投递。
- **轮次（round）**：每包盖当前轮次号。一次有效的通知缩包或超时缩包会让
  轮次 +1。旧轮次包的通知/超时只记录事件、**不再缩包**。超时若来自当前轮，
  载荷减一个步长（下限 1），并立即用新载荷重发最早的未确认连续段；
  超长通知则把载荷降到 `MTU - overhead`。
- **换线**：`active_line` 切换、`cur_payload = start_payload`、轮次 +1，
  然后调用 `resend_missing(kind="switch")` 立即重发全部未确认字节。
- **回执与去重**：ACK 把包区间加入 `AckedRanges` 的合并区间并集，
  返回本次“新增字节数”；重叠/重复区间新增 0，累计确认只按并集长度计算一次。
  超时后的在途包仍可“补到迟到回执”，并打 `late_ack` 标记。
- **重发只取未确认字节**：`AckedRanges.packetize_unacked(max_len)`
  跳过所有已确认区间，把未确认字节按当前载荷切成连续段；遇到已确认区间
  立即断段，所以重发包可能短于设定载荷。
- **分批连发**：`Drill.start_burst()` 只登记任务（含请求包数、批间隔）
  并立即返回，真正的发包由 `app.py` 里的后台调度线程反复调用
  `Drill.burst_tick()` 推进；每批最多 `BURST_BATCH_SIZE=5` 包，
  下一批最早在本批结束后 `interval_ms` 执行（首批不等待）。
  包上带 `burst_id`（单发为 `None`）。
  - 同一时刻只允许一个连发：重复提交返回 409；
  - `count="all"` 会换算成“剩余新字节所需包数”作为请求上限；
  - 连发期间单发同样只推进 `next_offset`，不占连发请求的包数；
  - 结束原因：`done`（请求包数发完）、`eof`（先到报表末尾，按实发数收尾）、
    `switch` / `shrink`（换线 / 有效缩包生效，剩余包停发）、
    `complete`（中途全部确认）、`reset`（重置）、`user`（手动停止）；
  - 结束后的快照保存在 `last_burst`，网页显示最近一次实发包数与结束原因；
  - 调度线程与请求线程共用 `app.py` 的同一把 `RLock`，状态不会读到半更新。
- **规模保护**：报表 ≤ 1,000,000 字节，最多 5,000 个包，批间隔 ≤ 60,000 ms；
  “连发全部”前先估算包数，超限直接 400 且不改状态。

## API 一览

| 方法/路径 | 作用 |
| --- | --- |
| `GET /api/state` | 完整演练状态 |
| `POST /api/reset` | 用 JSON 参数重置（空体=默认参数） |
| `POST /api/send-next` | 发下一包（优先推进新字节，否则补最早缺口；连发期间只推进新字节） |
| `POST /api/send-burst` | `{"count": 8, "interval_ms": 500}` 受理分批连发；`{"count":"all"}` 发完剩余新字节。立即返回 `accepted` + `burst`，不等发完 |
| `POST /api/burst/stop` | 手动停止进行中的连发 |
| `POST /api/resend-missing` | 按当前载荷重发全部未确认字节 |
| `POST /api/switch` | `{"line":"B"}` 换线、重置载荷并立即重发 |
| `POST /api/packets/<id>/ack` | 回执（支持超时后的迟到回执，重叠自动去重） |
| `POST /api/packets/<id>/timeout` | 触发超时（仅当前轮缩包并重发） |
| `POST /api/packets/<id>/deliver-notice` | 投递超长通知（旧轮通知被忽略） |
| `GET /healthz` | 健康检查 |

错误统一为 `{"ok": false, "error": "..."}`，400 参数/规模问题、404 包不存在、
409 当前状态不允许（如 ACK 一个实际已丢弃的包、传完后再发）。

## 推荐手动演练脚本

**A. 静默丢包（默认参数即是此场景）**

1. 默认 `报表 10000 / 起始载荷 1400`，A 线 `1500 / 120 / 通知关`
   （最大载荷 1380），B 线 `1500 / 60 / 通知开`（最大载荷 1440）；
2. 连发包数填 8，点“连续发包”：前面的满包显示红色“静默丢弃”，
   最后一个短包可能实际在途——这就是“小包能通、大包卡住”；
3. 尝试给红色静默丢包点 ACK 会被拒绝；对它点“触发超时”：
   载荷 `1400 → 1200`、轮次 +1，并自动重发 `[0,1200)`；
4. 对在途包任意顺序 ACK，再点“重发全部未确认”，直到绿色“全部传完”。

**B. 换线后的回包交错与重叠去重**

1. 可用测试里的参数：报表 `4200`，A 线开销 `200`（最大载荷 1300，通知关）；
2. 连发 3 包 → 对 `#1` 超时缩到 1200 → ACK 重发包 `#4` → “重发全部未确认”；
3. 在任何回执前点“换到线路 B 并立即重发”：载荷回到 1400，
   新包区间从尚未确认的 1200 开始，与 A 线在途包大面积重叠；
4. 用每包按钮按 `B#9 → 旧A#5 → B#8 → 旧A#6 → B#10` 的顺序回执，
   可看到累计确认 `2600 → 3800 → 4000（重叠只 +200）→ 4000（完全覆盖 +0）
   → 4200 传完`；给旧 A 线包补超时会提示“旧轮次不缩包”，但之后仍可迟到 ACK。

**C. 超长通知轮次**：点“预设：A 有超长通知”，连发 3 个满包后，
先投递任意一个通知：载荷一次性降到 1380；再投递同批其它通知，
会显示“过期轮次通知·已忽略”，不会重复缩包。

**D. 分批连发 + 网页插发/回执/换线**

1. 点“预设：长报表连发演练”（`报表 60000`，A 线开销 60、通知开），
   “应用参数并重置演练”；
2. 连发包数填 50、批间隔填 800ms，点“连续发包”：页面立即提示“已受理”，
   随后连发面板每批推进一次（约每 0.8s 多 5 包），可点“停止连发”中断；
3. 连发进行中点“发下一包”：新包紧接着连发已发到的位置发出，
   “最近一次连发”的实发数不受影响（单发不占连发包数）；
4. 给任一已发连发包点“回执 ACK”，累计确认照常增加；
5. 在下一批到来前点“换到线路 B 并立即重发”：连发立即以
   “换线生效，剩余包停发”结束，实发数停在停发前；再等超过批间隔也不会补发；
   旧连发包仍可回执、可触发超时（旧轮次只记录、不缩包）。

## 实测结果（完工前）

本环境没有 Docker 守护进程，因此镜像构建/Compose 起容器未能在此执行；
已完成的验证：

- `pytest`：**20 passed**，原有 10 项覆盖区间并集/打包、静默丢包→超时缩包→传完、
  通知每轮只缩一次、旧轮超时不缩包且可迟到 ACK、换线后乱序交错与重叠去重、
  完全重叠副本只计一次、连发全部、参数校验等；新增 10 项覆盖
  受理即返回+分批节奏、同一时间只允许一次连发、批间隔校验、
  连发期间单发取未首发字节且不占包数、到末尾按实发数收尾、
  换线/缩包/通知缩包/重置停发并记录原因、停发后旧包仍可回执、
  以及注入假时钟的分批确定性用例；
- 用 Dockerfile 同款命令 `gunicorn -w 1 --threads 8 -k gthread
  -b 0.0.0.0:8000 app:app` 真实启动，用 `/tmp/live_burst_check.py` 走查 6 组
  场景 **36 项断言全过**：提交连发 0.002s 返回受理、首批 5 包、
  进行中重复提交 409、期间单发起点=当时 `next_offset` 且不占包数、期间回执
  新增 1400、换线后停发且超时后不补发、旧包回执/旧轮超时 stale/迟到回执、
  超时缩包停发 reason=shrink、重置停发并保留快照、到末尾 eof 实发 3/请求 5；
- 用 jsdom 加载真实页面与 `static/app.js` 对接真实服务做 DOM 冒烟：
  **25 项断言全过、无 JS 错误**，覆盖连发面板 chip、按钮禁用/恢复、
  页面内单发、行内回执、页面换线停发与结束原因展示、2.5s 轮询重渲染；
- `compose.yaml` 通过 YAML 解析检查；`requirements.txt` 的版本区间
  对应实测可用的 Flask 3.1.3 / gunicorn 27.0.1。

## 限制与余项

- **单演练实例、内存态**：全局一把锁，刷新页面状态还在（同一服务进程），
  但重启即丢；不支持多房间/多学员隔离，如需多人同时使用要加 session/房间维度。
- 连发由**单进程内**的后台线程推进，所以仍须 `-w 1`：多 worker 时每个进程
  各有自己的调度线程与状态，连发只会在处理受理请求的那个 worker 里继续。
  进程重启时进行中的连发会随内存状态一起消失。
- 每批**固定最多 5 包**、批间隔只控制“批与批之间”的等待，不提供逐包间隔；
  首批立即发出，不受批间隔约束。
- 这是**协议行为仿真**，不发真实 ICMP、不操作真实网卡/路由；
  “上帝视角”的物理丢弃标记是教学设计，不是抓包结果。
- 超时由演练者手动触发（不做真实倒计时），便于确定性地演示乱序/交错；
  页面空闲时 2.5s 轮询、连发期间 0.5s 轮询，但没有自动超时。
- 本沙箱无 Docker，**`docker compose up --build` 未在本机实跑**；
  Dockerfile 仅做了同款 gunicorn 启动验证，首次在有 Docker 的机器构建时
  需确认网络可拉取 `python:3.12-slim` 与 pip 依赖。
- 未做鉴权与审计，仅限本地/可信教学网络；不要直接暴露到公网。
